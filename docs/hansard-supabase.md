# Hansard and services in Supabase

The public Hansard reader and admin editor use Supabase. The new catalogue starts empty; the 18 old Sanity Hansard records were **not transferred**. Sanity originals remain in the old dataset as an archive, and Sanity remains available for other activities.

Services were copied separately: 53 services, 6 categories, 4 providers and 1 linking-phrase record, plus 62 category links. One draft revision remains in the local migration backup. One downloadable file still uses its original Sanity asset URL; the record was transferred, not the file bytes. Backups and reports are in the ignored `.content-migration/` directory.

## PDF extraction contract

Use [`public/data/hansard-import-example.json`](../public/data/hansard-import-example.json) as the template. It is an illustrative draft, not parliamentary content. The admin editor also offers it as a download. The validator is [`lib/hansard/document.ts`](../lib/hansard/document.ts).

Return one JSON document per sitting with `schema_version: 2`, `sitting`, `sections`, `contributions`, and `sources`. Distinguish morning and afternoon sittings in the slug. Omit database row IDs when importing a new sitting. Use stable, unique `section_key` and `contribution_key` values containing letters, numbers, underscores or hyphens. Contribution order is unique across the entire sitting, not just within each section.

Extract verbatim text, speaker labels, debate headings, paragraph breaks, tables, page numbers and source metadata. Do not invent names, party affiliations, IDs, dates, missing speeches or summaries. Flag uncertain material for review. `source_page` is the one-based PDF viewer page index; a printed page/column label can go in `source_column`.

Use `body_html` for ready-to-display paragraphs, tables, lists and emphasis. Alternatively supply plain `body_text` with blank lines between paragraphs. On save, HTML is sanitized and searchable plain text is derived from it; when both are supplied, HTML takes precedence. The frontend displays that stored formatting. Sections may contain introductory text, but each speaker's speech belongs in a contribution. Do not duplicate speeches in section text.

Leave `leader_id` and `leader_role_id` null during extraction. Set `link_status: "unmatched"`, `review_status: "pending"` and sitting `status: "draft"`. Use `speaker_kind: "unknown"` when the speaker is uncertain. A collective response has `speaker_kind: "collective"` and `contribution_type: "collective"`. An identified non-member may use `link_status: "not-applicable"`.

## SQL import and foreign-key reference

Use [hansard-import.sql](hansard-import.sql) for a complete draft-only SQL import. The schema is already installed in Supabase. Replace the illustrative content; do not run table creation migrations again.

`select public.save_hansard_document($hansard$ { ...version 2 JSON... } $hansard$::jsonb);` returns the sitting UUID. For application code, pass JSON as a bound parameter (`$1::jsonb`) rather than concatenating generated text into SQL. Apostrophes inside the dollar-quoted JSON do not need SQL escaping; JSON double quotes and line breaks still need JSON escaping.

**One contribution row per speaking turn is essential.** Put each person's exact words in that row's `body_html` and the equivalent plain text in `body_text`. Put debate headings in sections. A single HTML blob cannot drive reliable speaker matching, speech links or member activity. The admin matches existing contribution rows; it does not automatically split an arbitrary whole-document HTML blob.

Unlike the admin save endpoint, the SQL function does not call the application's HTML sanitizer or derive plain text. Supply safe semantic HTML and matching plain text from your trusted extraction pipeline. The public renderer also sanitizes HTML, but empty `body_text` means missing search text and blocks publication. Admin JSON import is the simplest route when you want the app to do normalization for you.

Keep SQL imports `draft`, `pending`, source access `unknown`, with both member UUIDs null and links `unmatched`. Reload admin and select the new sitting in **Existing sitting**. Review and link speakers, then publish there. Direct SQL writes do not trigger Next.js path revalidation; admin publication does.

For updates, include the existing `sitting.id` and the **entire** document. This function replaces all child sections, contributions and sources; it is not a partial patch. Preserve `section_key`, `contribution_key` and the public slug. A repeated new import with the same slug but no sitting ID is rejected by the unique constraint.

| Foreign key | Target | Deletion behaviour |
| --- | --- | --- |
| `hansard_sections.sitting_id` | `hansard_sittings.id` | Cascade |
| `hansard_sections.(sitting_id, parent_key)` | `hansard_sections.(sitting_id, section_key)` | Deferred constraint; parent must exist in the same sitting |
| `hansard_contributions.sitting_id` | `hansard_sittings.id` | Cascade |
| `hansard_contributions.(sitting_id, section_key)` | `hansard_sections.(sitting_id, section_key)` | Deferred constraint; section must exist in the same sitting |
| `hansard_contributions.leader_id` | `leaders.id` | Set null, subject to publication/link guards |
| `hansard_contributions.leader_role_id` | `leader_roles.id` | Set null, subject to publication guards |
| `hansard_sittings.presiding_leader_id` | `leaders.id` | Set null |
| `hansard_sittings.presiding_role_id` | `leader_roles.id` | Set null |
| `hansard_sittings.county_id` | `counties.id` | Set null |
| `hansard_sittings.source_community_id` | `hansard_repository_communities.id` | No action; referenced community cannot be deleted |
| `hansard_sources.sitting_id` | `hansard_sittings.id` | Cascade |
| `hansard_sources.document_file_id` | `document_files.id` | Set null |
| `hansard_imports.sitting_id` | `hansard_sittings.id` | Set null |
| `hansard_imports.imported_by` | `auth.users.id` | Set null |

`leader_roles.leader_id` connects a historical parliamentary role to the person. Publication additionally checks that the selected role belongs to the selected person and covers the sitting date and house. Joint sittings allow either National Assembly or Senate roles. `source_collection_id` and `source_item_id` are external repository identifiers, not foreign keys into local tables.

Unique keys: sitting `slug`; section `(sitting_id, section_key)`; contribution `(sitting_id, contribution_key)` and `(sitting_id, sort_order)`. Contribution order starts at 1 across the whole sitting. Composite section foreign keys are deferred until transaction commit. The admin additionally checks section-tree cycles and import key formats.

## Member linking and editorial workflow

### Official source communities and access

The five National Assembly communities provided by the project owner are recorded in `hansard_repository_communities`: `id uuid` primary key, `title text`, `proceeding_type text`, `access_level text` (`public` or `restricted`) and `repository_url text`, all required. Public users can read only the three public community records.

| Official community | Public website behaviour |
| --- | --- |
| 01 House proceedings | Browse and publish reviewed public records |
| 02 Committee proceedings | Restricted; cannot publish, omitted from public navigation/search/member activity |
| 03 Joint sittings | Browse separately; link valid National Assembly or Senate roles on the sitting date |
| 04 State opening sittings | Browse separately as historical state openings before the 2010 Constitution |
| 05 Sessional bound volumes | Restricted; cannot publish, omitted from public navigation/search/member activity |

Access is explicit and independent of the repository's displayed count. A zero count is not interpreted as a licence to publish, nor is every empty public collection treated as restricted. No restricted source is fetched by this implementation. The registry follows the access classification supplied by the project owner; editors must verify the public accessibility of each source.

New imports default to `source_access: "unknown"`. Importing JSON or using Grok resets source verification. Check public accessibility in admin before publishing. Selecting a restricted community, mismatching a community's proceeding type, or selecting an internal proceeding blocks publication, even if `source_access` is falsely marked public. Database constraints enforce this independently of the form. Row-level policies also hide a previously published sitting and its child records if its community is later restricted. Senate and other public repositories may use a null National Assembly community ID while retaining their official source URL and verified access.

For joint sittings, `house_type` records the source/owning house and `proceeding_type` is `joint-sitting`. The admin picker and publication validator accept either chamber's role covering the sitting date. Joint records appear in both relevant house filters.

1. Open **Hansard** in your configured admin area (`/admin/hansard` is the internal route), import the extracted JSON or create a sitting manually.
2. Verify house, date, session and official source. Assign sections and correct formatted text.
3. For each MP/Senator/MCA, choose **Find / change parliamentary member**. Search by name or constituency. The database RPC `hansard_member_candidates(p_house, p_date, p_query)` returns only roles matching the house and covering the sitting date. No current-only profile matching is used for linking.
4. Confirm one contribution or all contributions with the exact same printed speaker name. Different people with similar names must be reviewed separately. If no eligible role exists, fix the member's history under **Officials** in the admin area; never invent a UUID or select an unrelated current office.
5. Check each contribution against the source PDF and mark its text reviewed. Check sitting metadata. Save drafts freely; use **Publish reviewed sitting** when complete.

Database validation also enforces review and historical-role checks when publishing, including status-only updates. Drafts, review and archived sittings are hidden from public queries. Child records inherit sitting visibility. Admin writes are authenticated and checked again in each API route; non-admin database users cannot edit these tables.

`save_hansard_document(p_document jsonb)` atomically saves the sitting and replaces its sections, contributions and sources. Existing `contribution_key` values must remain stable to preserve public links. Generated child row UUIDs can change during an edit. The admin form is for one editor at a time; it does not currently merge concurrent edits.

The existing `leaders` and `leader_roles` tables are the member directory used here. This is not a live synchronization with Parliament's website: role history must be maintained in the officials admin or an authorized ingestion pipeline. The source URL connects the record to the official publication.

The GitHub-style member pulse reads published Supabase contributions through the same public row-level policies. Each day links to that day's member contribution results, which link directly to the corresponding speech anchor in the sitting. Debate headings are carried into member results for section filtering. Chair interventions remain separate from floor-speech totals. A daily numeric table provides equivalent links alongside the colour grid, and the monthly table remains available. Missing linked records are explicitly not an attendance or performance measure.

### Citizen usability and accessibility

Public navigation distinguishes proceeding category, house, date and member. Dedicated Hansard full-text search is paginated and supports house/category filters; service search hits cannot crowd out debates. The published counts describe this site's collection rather than claiming the full official repository has been imported.

The frontend uses GOV.UK headings, labels, form controls, links, tables and details patterns. The global layout owns the main landmark and skip link; Hansard pages avoid nested main landmarks. Pulse links have descriptive names, GOV.UK focus styling and equivalent daily-table links with larger targets. These changes are not a certification of GOV.UK or WCAG compliance. Keyboard, screen-reader, zoom/reflow and user testing with representative citizens and real imported records are still required before making that claim. See the [GOV.UK Design System accessibility guidance](https://design-system.service.gov.uk/accessibility/).

Additional forward migrations: `hansard_source_access`, `hansard_public_search`, `hansard_source_policy_roles`. The extraction example includes the new provenance fields. Keep them when generating PDF extraction output.

## Grok

Grok is optional. A PDF extraction pipeline that produces this JSON does not require `XAI_API_KEY`. Manual editing, imports, linking, publishing and the public reader work without it.

The optional admin text-extraction action uses `XAI_API_KEY` and `HANSARD_XAI_MODEL` (existing default `grok-3-latest`). It sends pasted text to xAI and may incur API costs. It returns suggestions only; it does not publish or approve identities. The Grok adapter preserves extracted debate boundaries, printed constituency/party/capacity and time markers, and flags suggested chair turns for review. It never confirms identities. PDF upload is not handled by this action: extract text/OCR externally first. Review AI-generated headings, summaries and speeches against the PDF.

## Public routes and current scope

- `/government/legislature/hansard`: archive and full-text contribution search.
- `/government/legislature/hansard/sitting/<slug>`: formatted debates, section navigation, source pages and contribution anchors.
- `/government/legislature/hansard/member/<leader-slug>`: linked member contribution history.
- Legacy house/date links redirect to the sitting, or list multiple sittings on that day.

This establishes debate navigation and member histories similar to the referenced [OpenParliament](https://openparliament.ca/) and [UK Hansard](https://hansard.parliament.uk/) patterns. It does not claim feature parity: divisions/vote records, live parliamentary ingestion, automatic OCR, and PDF file hosting are separate future work.

## Pasted-text extraction follow-up

The extraction prompt is bundled in `lib/hansard/grok-prompt.ts`; Cloudflare no longer needs a filesystem read or a fetch to the public website to obtain it. The endpoint accepts the admin JSON text field, multipart text and `text/plain`. Input is limited to 300,000 characters per request. Each xAI request has a 120-second timeout.

The parser preserves short final chunks and validates the response shape, including nullable optional metadata. Truncated or malformed JSON is rejected rather than repaired by dropping unfinished speeches. Failed extraction leaves the editor document unchanged. Review every extracted speech against its source, especially when a long passage crosses chunk boundaries.

A live opt-in integration test sent a synthetic three-turn transcript through the actual POST handler and xAI, then converted the result to a validated admin document. It verified both debate headings, all three speeches, formatted paragraphs and unconfirmed member links. The admin authorization gate was mocked for that test; authorization is covered separately. No sitting was saved and no real parliamentary content was sent. Normal tests never incur xAI charges; the live test requires `RUN_HANSARD_GROK_LIVE=1` and a server API key.

Validation for the pasted-text fix: 165 automated tests passed (live test skipped by default); the opt-in live Grok test passed separately. TypeScript and focused lint passed. These latest parser changes have not been deployed; rebuild the production bundle before publishing them.
